# Implementation Plan: NF-e SP Production Authorization

**Branch**: `main` (feature branch `025-nfe-sp-producao` was not created) | **Date**: 2026-10-10 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/025-nfe-sp-producao/spec.md`

## Summary

Enable the existing root `authorizeNFe` operation to submit a verified SP issuer NF-e to the normal SP production authorizer, while preserving homologation behavior and current result classifications. Route authorization and known-receipt continuation through an authorizer-aware transport catalog; reject missing, contradictory, non-SP, or mixed-batch identity before network I/O. Production must use an integrator-provided executor configured for mutual TLS. SVC-AN remains an explicit contingency boundary, never an automatic fallback.

## Technical Context

**Language/Version**: TypeScript 6.0.3 strict, ESM; Node.js >=18.18.

**Primary Dependencies**: Existing TypeScript, Jest 30, ESLint 9, Prettier 3, `@xmldom/xmldom`, `node-forge`, and `xml-crypto`; no new dependency expected.

**Storage**: None. Routing, authorization, and receipt reconciliation remain stateless.

**Testing**: Jest 30 with fixtures and injected `RequestExecutor`; no live SEFAZ transmission.

**Target Platform**: Node.js ESM consumers on supported Node.js versions.

**Project Type**: Published npm SDK/library with one root ESM export.

**Performance Goals**: Preserve the current one-request authorization path and default 5,000 ms transport timeout; no polling or additional network probe.

**Constraints**: SP (`cUF` 35) normal authorizer only. Production identity, environment, authorizer, and endpoint must agree. The official MOC requires TLS 1.2 or later with mutual certificate authentication; the default `fetch` executor does not configure client certificates, so production requires an injected mTLS-capable executor. Do not expose credentials/private key material, silently fall back to SVC-AN, or retry an uncertain submission.

**Scale/Scope**: Existing NF-e single and batch authorization plus one-shot continuation for a known `nRec`; no other UFs, services, or automatic receipt polling.

**Knowledge Sources**: Primary: `SRC-RH-002` (MOC 7.0, consulted 2026-05-19), `SRC-NFE-003` (SEFAZ/SP NF-e overview), `SRC-NFE-004` (SEFAZ/SP NF-e services), and `SRC-NFE-006` (national official Web Services table, consulted 2026-10-10). No secondary source used. The official table supplies the SP authorization and receipt endpoints; dynamic live availability and each issuer's credential/permission state remain external prerequisites, not facts inferred by this plan.

## Implementation Gates

1. Confirm `payload.cUF` and the access-key UF agree when both exist; derive UF from a valid 44-digit access key when present. Require an unambiguous SP identity for production and require every item in a batch to resolve to SP. Missing, malformed, conflicting, non-SP, or mixed identity must fail before invoking the executor.
2. Resolve both `nfe-authorization` and `nfe-authorization-batch` with provider `SP` in production. Propagate the existing explicit authorizer in the 021 receipt routing context so reconciliation reaches SP's `NFeRetAutorizacao4` endpoint.
3. Require authorization and receipt responses to identify production (`tpAmb` `1`) before mapping success. Malformed XML, authorization status `100`/`104` without `nProt`, status `103` without `nRec`, or terminal receipt authorization without `nProt` is `protocol-error`; preserve existing receipt classifications and prohibit blind resubmission or automatic contingency switching after timeout/unavailability.
4. Require a caller-supplied mTLS-capable request executor for production; keep default `fetch` available for existing non-production behavior. Preserve non-secret diagnostic metadata but redact credential values and certificate/private-key bytes from returned envelope evidence. Treat credential validity and live availability as external conditions; report handshake/transport failure without claiming authorization.
